The Semantic Backup Layer: Role and Relation to the AST-Based Structural
Model

1. What the structural (AST) layer already does

The core system — the subject of the published paper — extracts
programming competencies directly from a submission's Abstract Syntax
Tree. Every competency is defined as an explicit, rule-based pattern
over primitives (loops, tests, assignments, etc.), scored along two
independent axes, coverage and structure, multiplied into a final_score.
This is:

-   Deterministic — the same code always produces the same score

-   Fully inspectable — every match traces back to specific AST nodes
    and named bindings

-   Validated at real scale — against thousands of real Refactory
    submissions and an unseen course assignment

Its one structural limitation, named explicitly in the paper's own
Limitations section: it can only recognize strategies someone has
written a rule for. A student who solves a problem in a way no one
anticipated — using a language feature or idiom the rule set doesn't
cover — will score 0, even if their code is completely correct.

Concrete example already named in the codebase: finding the maximum of a
list via functools.reduce(lambda a, b: a if a > b else b, lst). This has
no ast.If, no explicit loop, and no max()/min() call — invisible to both
branches of FindExtremum = ANY(manual_loop, builtin_reduce), even though
it's a legitimate, correct implementation of the exact skill that
competency is trying to detect.

2. What the semantic backup layer is for

The semantic layer exists only to catch this specific failure mode: a
submission that is very likely correct, but that the rule-based
structural layer cannot recognize because no one has written a rule for
its particular strategy yet.

It works by comparing a submission's code embedding (currently via
Salesforce/codet5p-110m-embedding, a model trained with a contrastive
objective specifically for code similarity/retrieval) against a small
registry of known-correct exemplar solutions for a given competency. A
high similarity score means: this looks like it's doing the same thing
as a correct reference solution, even though no structural rule matched
it — a signal that a human should take a second look, not proof of
correctness.

3. The one design rule that defines the relationship between the two
layers

Semantic similarity never modifies final_score.

This is stated as a non-negotiable principle in the code itself
(semantic_backup.py) and is the single most important fact about how the
two layers relate. Structural evidence remains the sole, inspectable
basis for the score every competency reports. The semantic layer only
ever adds a separate, clearly labeled, explicitly "unverified" field —
reported alongside the structural score, never folded into it — intended
to flag a submission for manual review, not to auto-credit it.

The reasoning: the structural layer's entire value proposition,
established and validated across the AST paper, is that every score is
traceable to a specific, inspectable pattern in the code. Letting an
embedding-similarity number — which is not inspectable in the same way,
and which the paper's own early tests showed can fail in non-obvious
ways (see §5) — silently raise a final_score would undermine exactly the
property that makes the structural layer trustworthy in the first place.
Keeping the two strictly separate lets the system gain semantic-layer
sensitivity without spending any of the structural layer's
inspectability or reliability to get it.

5. Why the semantic layer isn't in the published (AST) paper

Two reasons, both already stated explicitly in that paper's own text:

1.  Scope discipline. The AST paper's contribution and validation claims
    are about the structural model specifically. Folding in a second,
    architecturally separate signal — with its own, still-open
    validation question — would dilute a paper that is otherwise fully
    validated at real scale.

2.  It genuinely wasn't validated yet at the time. The original
    development sandbox had no network access to download real
    codebert-base weights (confirmed via a blocked request, not
    assumed). The stand-in used to test the surrounding plumbing
    (registry, caching, thresholding, report integration) was a
    bag-of-AST-tokens cosine similarity, and it was directly shown to
    have no discriminative power — a genuinely related reformulation and
    a completely unrelated function scored within 0.02 of each other.

The current Colab work is precisely the process of closing that gap: get
real embeddings running, build a real exemplar registry from actual
Refactory solutions, and test — honestly — whether real code-similarity
embeddings separate genuinely-novel-correct submissions from
genuinely-wrong ones.

6. Current state of that validation (in progress)

-   First real-embedding attempt (raw codebert-base, mean-pooled):
    reproduced the same "no discriminative power" finding as the
    original stub — related and unrelated code scored ~0.96 either way.
    Root cause: anisotropy — raw, non-fine-tuned transformer embeddings
    collapse into a narrow cone in embedding space under mean-pooling, a
    documented property of BERT-family models used this way,
    independently reproduced by other users hitting the identical
    symptom with codebert-base.

-   Switched to codet5p-110m-embedding, a model actually trained with a
    contrastive objective for code similarity (not just masked-language
    modeling) — the same fix Sentence-BERT applied to regular BERT. This
    is now producing a real, non-collapsed gap between related and
    unrelated code in the sanity check.

-   Building the actual test set that matters: not "everything," but
    specifically submissions that are test-suite-correct yet scored 0
    structurally (43 real Q5 candidates found so far) versus a
    true-negative comparison group.

  The first attempt at a comparison group (same-exercise "wrong"
  submissions) turned out to be contaminated — per the AST paper's own
  §5.3 finding, most wrong-labeled submissions still implement the
  structural pattern correctly and fail elsewhere, so they aren't real
  negatives for this test. Comparison group is being rebuilt from an
  unrelated exercise instead, to get an unambiguous negative set.

-   Next step: compute similarity for both groups, run an AUC/ROC sweep
    to see whether real similarity actually separates them, and
    calibrate a threshold from that — rather than assuming one. Either
    outcome (it works, or it doesn't beat chance) is a valid, reportable
    finding for the companion paper, in the same honest spirit as Table
    4 of the AST paper.

7. One-sentence summary of the relationship

The AST layer is the system's source of truth; the semantic layer is a
secondary, explicitly-unverified sensor that watches for cases the
source of truth is structurally blind to, and its entire validation
burden is to prove it can do that reliably enough to be worth reporting
at all — it can never buy its way into affecting a score.

similarity to every centroid, including its own. The signal that
actually separates "novel" isn't "which centroid is nearest" — it's "how

overall, so manual's broad, generic pull wins the argmax even though it
structurally scored 0. A submission that's genuinely alien to all three
categories drags every similarity down together, and only then does
novel surface as the winner by default.

semantic-backup layer, not just this validation exercise: a pure

detecting novelty specifically. What you actually want is closer to
anomaly detection: flag as novel when max(sim_manual, sim_builtin) drops

that comparison. That reframes it from a 3-way classification into "does
this look enough like any known strategy — if not, flag it," which is a
