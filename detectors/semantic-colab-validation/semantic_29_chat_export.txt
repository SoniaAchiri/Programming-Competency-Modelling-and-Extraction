Why this happens

codebert-base was trained with masked-language-modeling and
replaced-token-detection objectives — not with any objective that makes
cosine similarity between pooled embeddings meaningful. When you
mean-pool raw transformer output like this, the resulting vectors don't
spread out across the embedding space the way you'd want; instead they
collapse into a narrow cone, so almost everything ends up with high
cosine similarity to almost everything else, regardless of actual
content. This is called anisotropy, and it's a documented property of
BERT-family models used this way — there's literally an open issue on
the microsoft/CodeBERT GitHub repo where someone hits this exact symptom
(very high, non-discriminative cosine similarity for randomly chosen
code pairs) using essentially the same pipeline as your notebook.

So — ironically — you've now reproduced the same finding as the stub
embedding in the original sandboxed version (no discriminative power),
but for a different, legitimate reason: it's not that CodeBERT is bad at
understanding code, it's that raw mean-pooled CodeBERT embeddings aren't
a similarity metric.
